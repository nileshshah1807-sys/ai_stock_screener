Below is a practical explanation of each P0 requirement, specifically mapped to your Model 5.0 NSE stock screener. The goal of P0 is to answer one question honestly:

If Model 5.0 had been running in the past using only information actually available at that time, would its top-ranked stocks have outperformed after realistic trading costs?

1. Build point-in-time statement history
What “point-in-time” means

For every historical screening date, the model must only use financial information that was publicly available on or before that date.

For example:

Company reports FY2024 results on May 20, 2024
You simulate a Model 5.0 run on April 30, 2024
FY2024 results must not be visible
The latest usable annual statement might still be FY2023

If your current database contains FY2024 data without its publication timestamp, the backtest could accidentally use that data in April 2024. This is called look-ahead bias.

Point-in-time data is one of the most important protections against look-ahead bias in fundamental backtesting.

What you should store

Each statement record should include:

symbol
financial_period_end
statement_type
publication_date
exchange_filing_timestamp
data_available_from
source_document_url
source_document_hash
ingested_at
statement_version
is_restated


Example:

Symbol: TCS
Financial period: FY2024
Period end: 2024-03-31
Publication timestamp: 2024-04-12 16:47 IST
Data available from: 2024-04-13
Statement version: Original

Publication time matters too

Suppose results were filed at 5:30 PM on May 10. They were not available during normal market hours on May 10.

A conservative rule is:

If statement published before market close:
    usable from next trading session

If statement published after market close:
    usable from next trading session


For a daily-bar model, using the information beginning from the next completed trading session is safer and easier to audit.

Recommended selection rule

For each backtest date:

Select the newest statement where:

data_available_from <= model_decision_timestamp


Do not select statements merely using:

financial_period_end <= model_date


The financial year may have ended on March 31, but investors may not receive the report until May.

Why this affects Model 5.0 significantly

Model 5.0 depends heavily on quality and growth:

ROE or ROIC
Revenue growth
Profit growth
Margin behavior
Leverage
Earnings consistency
Cash-flow conversion

If you accidentally use newly published or revised figures, quality and growth scores can become significantly more accurate in the historical backtest than they would have been in real time.

2. Store original and restated values separately
What is a restatement?

A company may revise an earlier financial statement because of:

Accounting-policy changes
Merger or demerger
Reclassification
Error correction
Revised segment reporting
Regulatory direction
Comparison-period adjustments

A present-day data provider may show only the latest corrected value.

Example

Assume the company originally reported:

FY2023 PAT = Rs 800 crore


A year later, it restated FY2023 as:

FY2023 PAT = Rs 620 crore


When simulating a screening run from June 2023, you must use ₹800 crore because ₹620 crore was not known then.

If you use the restated number, your model is using future knowledge.

Suggested storage model

Do not overwrite old records. Store versions:

statement_id
symbol
financial_period
metric
reported_value
published_at
version_number
supersedes_version
is_restatement
source_hash


Example:

Version 1:
FY2023 PAT = 800
Published = 2023-05-15

Version 2:
FY2023 PAT = 620
Published = 2024-04-20
Restates version 1


Then:

June 2023 backtest receives version 1
May 2024 backtest receives version 2
Current screening receives the latest valid version
Two useful analytical outputs

You can later measure:

As_Reported_Score
Latest_Restated_Score
Restatement_Impact


A company that repeatedly restates financial results may itself deserve a data-quality or accounting-risk flag.

Minimum viable alternative

If building complete version history is currently too expensive, apply a conservative reporting lag:

Annual results: usable 90 to 120 days after year-end
Quarterly results: usable 45 to 60 days after quarter-end


This is less accurate than actual publication timestamps, but safer than using unrestricted current data.

3. Reconstruct historical universes, including delistings
The incorrect approach

Suppose today you have 2,300 NSE symbols. You take these symbols and backtest Model 5.0 from 2015.

This implicitly asks:

Among companies that survived until 2026, which ones would the model have selected in 2015?

That is not the real 2015 investment universe.

It excludes companies that:

Were delisted
Failed financially
Were suspended
Were acquired
Merged into another company
Changed identifiers
Lost liquidity
Entered insolvency
Disappeared due to poor performance

Using only surviving securities can inflate historical performance and suppress observed risk.

What the historical universe should answer

For each rebalance date:

Which securities could an investor actually buy on that date?


A symbol should qualify only if:

It was listed on that date
It had sufficient completed price history
It was not suspended
It passed the applicable historical liquidity rule
Its required data was available
It was not already under delisting
The security identifier maps correctly through corporate actions
Example

Assume your current universe is:

ABC
DEF
GHI


But the actual 2018 universe was:

ABC
DEF
OLDCO
FAILEDCO


Testing 2018 using only today’s universe omits OLDCO and FAILEDCO. If those companies had weak fundamentals and later collapsed, excluding them makes the model look safer than it was.

Delisting return treatment

You need an explicit policy:

Acquisition or merger

Use the cash or security consideration received by shareholders.

Voluntary delisting

Use the final realizable exit price where available.

Distress or insolvency

Do not carry the last quoted price forever. Apply the eventual recovery value, potentially zero, when appropriate.

Long suspension

Mark the position as non-tradable and apply a conservative recovery policy.

Without such rules, a failed company can disappear from your results without its loss entering portfolio returns.

Data you need

Maintain a security master:

security_id
symbol
ISIN
listing_date
delisting_date
delisting_reason
symbol_valid_from
symbol_valid_to
previous_symbol
successor_security_id
suspension_periods
corporate_action_type


Use ISIN or an internal permanent ID as the primary identifier. Symbols alone are unsafe because symbols can change or be reused.

4. Run walk-forward 1/3/6/12-month return tests
What not to do

Do not calculate scores for the full historical period, adjust the weights until the results look good, and then report performance on that same period.

That is an in-sample optimized backtest.

You may unintentionally discover weights that match historical noise rather than a repeatable relationship.

What walk-forward testing means

Time must move only forward.

For example:

Development period: 2014-2018
Validation period:  2019
Development period: 2014-2019
Validation period:  2020
Development period: 2014-2020
Validation period:  2021
Development period: 2014-2021
Validation period:  2022


This imitates production use: parameters are chosen from historical information, then tested on a future period not used to choose them. Walk-forward analysis is used to detect whether performance persists outside the period used for model development.

For your first validation, do not re-optimize every year

Model 5.0 already has chosen weights:

Quality  = 35%
Growth   = 20%
Value    = 15%
Momentum = 25%
Risk     = 5%


For the cleanest first test:

Freeze those weights.
Generate the historical score on every rebalance date.
Hold the selected portfolio forward.
Measure future outcomes without changing parameters.

Later, you can test expanding-window recalibration separately.

Why test multiple horizons?

Different factors work over different horizons.

1-month forward

Tests very short-term ranking behavior. It may be noisy and sensitive to momentum reversals.

3-month forward

Useful for quarterly rebalance behavior and earnings cycles.

6-month forward

A suitable medium-term horizon for quality, value, and momentum interaction.

12-month forward

Tests whether the fundamental thesis translates into longer-term returns.

Forward-return calculation

If the model uses a completed bar on date t, do not assume you can buy at that same closing price.

A conservative implementation is:

Signal date: completed close on day t
Entry price: next trading day's open or VWAP
Exit price: corresponding future open or VWAP


Filling at the same close that generated the signal can introduce look-ahead or unrealistic execution assumptions.

What should be evaluated?
Cross-sectional predictive power

Calculate Spearman rank correlation between:

Model score on date t
and
Forward return after 1/3/6/12 months


This is commonly called rank IC.

Interpretation:

Positive IC:
higher-ranked stocks generally outperform lower-ranked stocks

IC near zero:
ranking has little predictive relationship

Negative IC:
higher-ranked stocks tend to underperform


Do not judge only by average IC. Check:

Median IC
Percentage of positive periods
IC volatility
Worst rolling period
IC by market regime
IC by sector
IC by market-cap segment
Bucket analysis

Divide the universe into five or ten score groups:

Decile 1 = highest score
...
Decile 10 = lowest score


A healthy ranking should ideally show a reasonably monotonic pattern:

D1 return > D2 > D3 ... > D10


Perfect monotonicity is unlikely, but the top groups should consistently outperform the lower groups.

Portfolio analysis

Test at least:

Top 10
Top 20
Top 50
Top decile
BUY and STRONG BUY only

Report:

CAGR
Benchmark-relative return
Volatility
Sharpe ratio
Maximum drawdown
Hit rate
Turnover
Number of holdings
Sector concentration
Market-cap concentration

5. Include costs, turnover, slippage, and liquidity capacity

A stock-ranking model can be statistically correct but operationally unusable.

Transaction costs

Include all applicable expenses, such as:

Brokerage
Securities Transaction Tax
Exchange transaction charges
GST on applicable charges
SEBI charges
Stamp duty
DP charges on sales

Do not hard-code today's charges for the full historical period if charges changed materially over time. Ideally, maintain cost schedules with effective dates.

Turnover

Portfolio turnover measures how much of the portfolio is replaced at each rebalance.

Example:

January portfolio: A, B, C, D, E
February portfolio: A, B, F, G, H


Three of five positions changed, creating significant turnover.

A simple one-way turnover definition is:

Turnover_t = 0.5 * sum(abs(new_weight_i - old_weight_i))


If monthly turnover averages 40%, your annual traded notional can become very high. A small gross excess return may disappear after trading costs.

Slippage

Slippage is the difference between the assumed and actual execution price.

It depends on:

Bid-ask spread
Daily turnover
Volatility
Order size
Trading frequency
Price gaps
Execution timing

Slippage and spread can matter more than brokerage, particularly for small and illiquid securities.

A practical model could use:

Estimated_Cost =
explicit_fees
+ half_spread
+ liquidity_impact
+ volatility_buffer

Liquidity capacity

Capacity answers:

How much money can this strategy manage before its own trading materially damages performance?

Your existing median-turnover and build-days fields can support this.

For every proposed order:

Participation_Rate =
Order_Value / Median_Daily_Traded_Value


For example:

Target order       = Rs 5 lakh
Median daily value = Rs 50 lakh
Participation rate = 10%


That is materially less realistic than a 1% participation assumption.

Test several portfolio sizes:

Rs 10 lakh
Rs 50 lakh
Rs 1 crore
Rs 5 crore
Rs 10 crore


For each size, report:

Number of actionable stocks
Average build days
Maximum build days
Expected slippage
Net return after impact
Percentage of portfolio violating capacity limit
Report gross and net results separately
Gross CAGR
Explicit cost
Slippage cost
Market-impact cost
Net CAGR


This makes it clear whether the model identifies returns or merely generates too much trading.

6. Freeze Model 5.0 before the final untouched test
The problem

Suppose you test Model 5.0 on 2016-2025 and discover:

Quality weight 35% performs better than 25%
Momentum 25% performs better than 20%
MA200 works better than MA150
BUY threshold 60 works better than 58
Quarterly rebalance works better than monthly

After repeatedly modifying the model using 2016-2025, that entire period becomes training data.

You cannot then claim 2016-2025 as independent validation evidence.

What freezing means

Before opening the final test period, create a model specification containing:

Model version: 5.0.0
Factor definitions
Factor weights
Winsorization rules
Missing-data rules
Universe rules
Rebalance frequency
Benchmark
BUY thresholds
STRONG BUY thresholds
Coverage gates
Liquidity rules
Transaction-cost assumptions
DCF policy


Persist:

Git commit SHA
Configuration hash
Dataset version
Calendar version
Statement-data version
Backtest-engine version


Then prevent parameter changes until the final test report is generated.

Suggested chronological split

Illustrative example:

2014-2020: Research and development
2021-2023: Validation and limited adjustment
2024-2025: Final untouched historical test
2026 onward: Live shadow validation


The exact years depend on your available data, but the order must remain chronological.

If you change the model after the final test

That is allowed, but it becomes a new model:

Model 5.1


Its previous final test is no longer fully independent evidence for the changed model.

This versioning discipline prevents quiet overfitting.

B. Equal-weight universe
Question answered

Is the model adding value, or did the average NSE stock perform well?

Suppose small-cap stocks had a very strong period and your model mainly selected small companies. Beating the Nifty 500 might simply reflect size exposure.

An equal-weight eligible-universe benchmark uses the same historical universe and eligibility rules as your strategy, but gives every stock equal weight.

This controls partially for:

Breadth
Universe construction

The benchmark must use the same point-in-time universe as Model 5.0.

D. Quality-only

Build a ranking using only the Model 5.0 quality block.

Question answered

Is most of Model 5.0's performance coming from quality?

If quality-only performs as well as the complete model, growth, value, momentum, and risk may not be adding useful information.

Do not change the quality calculation for this test. Use the exact Model 5.0 quality block.

E. Momentum-only

Use only the momentum block:

6-month relative strength
12-month or 12-minus-1-month relative strength
MA200 trend state

Question answered

Is Model 5.0 primarily a momentum strategy with fundamental decoration?

Momentum is a documented factor, but it can experience abrupt reversals and higher turnover. Professional factor methodologies often measure momentum through risk-adjusted 6- and 12-month excess returns, frequently omitting the most recent month to reduce short-term reversal effects.

Compare:

Bull-market performance
Bear-market performance
Sharp rebound performance
Turnover
Crash or reversal periods

Use only the value block.

Question answered

This also helps test whether your current valuation factor is being overwhelmed by quality and momentum.

Evaluate value using multiple measures rather than only P/E:

Question answered

Does Model 5.0's complexity add value beyond a simple, understandable model?

A complex model should justify itself through at least one of:

Higher net return
Better drawdown
Better rank consistency
Lower sector concentration

Fewer severe failures
Better data-quality behavior

If simple quality-momentum performs similarly, prefer the simpler system or use Model 5.0 only where it provides demonstrable incremental benefit. Combining multiple factors can improve diversification, but complexity must be validated rather than assumed beneficial.

Bottom line

P0 is not intended to prove that Model 5.0 produced attractive historical numbers. It is intended to make it difficult for the model to cheat accidentally.

If Model 5.0 performs well only with current survivors, latest restated statements, same-close execution, and zero trading cost, it has not established reliability. If it still performs well using point-in-time statements, historical universes, next-session fills, realistic costs, simple benchmark comparisons, and an untouched final test, then you have meaningful evidence that the ranking may contain a genuine predictive signal.
